    What the report measures

    Each engine runs in a fresh child process and receives the same deterministically sorted SVG inputs. The report includes wall time and Node process user/system CPU time for the transform loop, plus core-equivalent utilization (process CPU time divided by wall time; it is not whole-system CPU utilization), sampled peak resident set size (RSS), output bytes, output SHA-256, success/failure count, Node/package versions, and a fixture digest. Input loading, package import/startup and filesystem writes are excluded from timing; RSS includes the imported runtime and package baseline. RSS is sampled every 10ms and may miss short peaks, so it is not exact peak memory consumption.

    Fair interpretation

    Both engines generate React JavaScript in memory with a documented configuration. Different products can have different semantics, optimization defaults, error handling and generated output; this workload is not a security-equivalence test. If either implementation fails any input, the report shows counts and withholds a wall-time winner. Otherwise it reports the lower measured wall time for this run only. Do not treat results as a universal ranking or guaranteed advantage.

    Alternative implementation

    This comparison uses SVGR's @svgr/core and JSX plugin, version-pinned in the benchmark-only tool. Installing them does not modify SVGER-CLI's runtime dependencies or published package.
